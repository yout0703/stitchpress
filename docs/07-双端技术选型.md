# 双端技术选型

用户已明确希望发布两个平台版本。产品目标为 **Windows 和 macOS 桌面APP**，共用业务核心、项目格式与主要交互；不是两套独立功能线。现有dev2采用PySide6 Widgets/Python/uv/独立进程，Mac已有构建证据，Windows未验收。v0.5只调整功能优先级，不引入新技术栈；正式双端范围仍需验证。

资料核对：2026-11-11，通过Context7检索并查看官方页面。

### 平台定位与开发安排

用户补充：客户仅使用Windows，我们在macOS开发调试。Windows是客户交付、操作体验与最终验收的主平台；macOS提供同业务能力的开发调试版本，保留双端可运行目标，不由此推定存在Mac客户的商业支持需求。

两端共用页面结构、操作顺序、字段、校验和任务逻辑；只把快捷键、系统对话框、菜单位置、路径与权限等差异放入平台适配。Qt Widgets默认可使用不同平台样式；若选Widgets路线，优先验证共享Fusion基础样式加统一主题/图标/间距，避免依赖某平台独占样式。字体栅格、窗口装饰和系统对话框仍可能不同，不承诺屏幕截图逐像素一致。[Qt样式机制](https://doc.qt.io/qtforpython-6/PySide6/QtWidgets/QStyle.html)

保存/复制等操作采用标准快捷键语义，在Windows显示Ctrl组合、Mac显示对应Command组合；文件选择框可遵循系统习惯。鼠标框选、滚轮缩放、表格编辑等高频制版动作由应用统一定义并双端检查。[Qt标准快捷键](https://doc.qt.io/qtforpython-6/PySide6/QtGui/QKeySequence.html)、[Qt文件对话框](https://doc.qt.io/qtforpython-6/PySide6/QtWidgets/QFileDialog.html)

开发日常在Mac运行共享代码；从E0起准备Windows x64构建与测试环境（远程Windows电脑或构建执行器均可），小样阶段就验证启动、预览、鼠标操作和完整导出。Windows安装包在Windows环境构建；Mac调试通过不代表Windows验收通过。构建执行器可做自动检查，交互体验仍要在Windows桌面验证；ARM环境的模拟运行不能单独代替目标x64环境验收。

每个里程碑在Windows检查中文字体、100%/125%/150%缩放、路径与文件占用、图像编解码依赖、安装及目标读取软件。正式客户操作说明与教程截图以Windows版为准，产品页面不显示面向开发者的跨平台实现细节。

## 1 必须满足的约束

- 客户无需自行安装Python或配置开发环境；应用随包携带必要运行依赖。
- 本地处理母版和大型TIFF，长任务不阻塞界面；项目可在双端交换。
- 精确十进制尺寸、ICC、图块、字体与PDF版式不能依赖某台机器的系统默认。
- 首发至少验证Windows x64和macOS Apple Silicon；macOS Intel是否加入首发待设备调查和构建验证，不把两个平台误写成只有两种CPU构建。
- 最低OS版本在候选框架及依赖试验后明确公布，不预先声称兼容所有Windows/macOS。
- Python依赖使用uv；如采用Web界面技术，其前端使用pnpm。
- R1只以参考本地后期功能为主；真实AI接入与评估归R2，不作为一期选型/开发/验收前置，已有AI适配代码保留。

## 2 候选方案

| 方案 | 结构 | 对本项目的判断 | 需验证的成本 |
|---|---|---|---|
| A：PySide6桌面界面＋Python核心 | 同一语言的UI与独立工作进程 | 优先验证；便于整理已有Python生产逻辑，减少桥接层 | 大图视口、表格编辑、界面质感、打包及字体资源 |
| B：Tauri桌面壳＋Web界面＋Python工作进程 | Web UI、桌面宿主、每平台打包的Python sidecar | 保留为候选；适合重视Web界面布局/后续复用的方向 | 多技术栈、IPC、sidecar分平台打包、WebView显示与资源权限 |
| C：浏览器＋服务端生产 | 上传项目到服务或连接本机服务 | 不作为首发默认；离线、安装体验和大文件往返需额外方案 | 服务运维、上传、账号、网络与客户资源管理 |

先验证A的小样，理由是现有核心主要为Python，双端发行仍需验证。只有大图交互、表格编辑或双端发行在合理修正后仍无法满足验收，才记录具体缺口并启动B的同样本对照，不要求预先开发两套界面。这个优先顺序是项目判断，不是官方性能结论。

### 2.1 当前主要技术方向（v0.4）

**推荐验证主线：PySide6桌面界面＋Python本地业务核心＋独立工作进程＋可替换的云端AI适配器。** A是当前推荐，B是保留备选；正式框架和依赖版本仍须E0试验后冻结。

| 层次 | 当前方向 | 决策状态与验证重点 |
|---|---|---|
| 桌面界面 | PySide6 / Qt | A优先验证；Qt Widgets与Qt Quick的取舍由大图选区、表格、缩放原型决定，尚未锁定 |
| 业务核心与依赖 | Python＋uv | 共用计数、尺寸、布局、任务和AI编排；Python版本按双端依赖支持冻结 |
| 针格与图像 | NumPy、Pillow/ImageCms候选 | 原脚本已有相关逻辑；Pillow色彩转换用于验证10第5.1节，量化策略由本地转换器明确指定 |
| TIFF | 对照Pillow现有LZW路径与tifffile流式候选 | 用真实CMYK/LZW/ICC、大图分条和双端发行验证后选择；编解码依赖一起锁定 |
| PDF | ReportLab＋pypdf为复用候选 | 原导出器使用；是否保留由CMYK嵌入、倍率及读回验证决定，PDF实际渲染检查器另选 |
| Excel | openpyxl为候选 | 表格生成与检查，公式重算/缓存及渲染工具需另验证，不能假设写出公式就有计算结果 |
| 本地数据 | 版本化JSON/矩阵资源＋自包含作品容器 | 业务契约已定义；容器编码未冻结，作品索引可重建；提交协调器统一写入和冲突检测 |
| 长任务 | 独立工作进程＋受控消息 | 进程仅提交结果事件，项目写入归协调器；具体进程通信实现待小样确认 |
| AI | 理解/生成/编辑能力适配器＋阶段任务 | 二期验证真实组合；已有DeepSeek Flash BYOK配置，图像供应商待接入 |
| 发布 | A路线优先验证pyside6-deploy/Nuitka | Windows x64与macOS arm64分别构建；签名、安装容器与最低OS在E0明确 |

表中的图像、TIFF、PDF、Excel库是现有逻辑的复用候选，并非已经通过全部要求的正式依赖清单。本轮核对了Qt/Tauri部署与Pillow ICC机制；其余库的API、版本和发行能力在进入对应实现前查询官方资料并验证。

只有选B时才引入Web前端与Rust宿主，前端依赖用pnpm；当前未选React/Vue等前端框架。托管AI如被选中，需要独立服务端，云平台与数据库也尚未选型；本地生产不依赖该服务端。

## 3 官方资料支持的能力

Qt for Python提供 `pyside6-deploy`，以Nuitka为部署基础，面向桌面平台产出应用；Windows可得到exe及依赖目录，macOS使用app包。它解决应用部署的一部分，不自动完成客户资源整理、平台签名和安装体验。[Qt官方部署文档](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html)

Tauri提供外部可执行程序sidecar机制，并将Python程序列为使用场景。每个目标平台/架构需要相应二进制，按target triple对应；只写一份 `externalBin` 配置不会自动把Python转换成所有平台程序。[Tauri官方sidecar文档](https://v2.tauri.app/develop/sidecar/)

Tauri还提供平台安装包的构建/分发入口；平台签名和发布是独立环节。[Tauri官方分发文档](https://v2.tauri.app/distribute/)

以上是框架能力依据。具体版本、最低OS、CPU、渲染器依赖与最终安装包大小由本项目验证后记录，不据文档示例锁定版本号。

2026-11-11修订时通过Context7再次核对：Qt部署器以Nuitka为基础，Tauri侧载程序按目标平台/架构准备；Pillow/ImageCms提供源ICC到目标ICC的转换，alpha须按处理模式显式保留。应用采用10第5.1节的独立alpha契约，不能假设RGBA转RGB仍有透明度。[Pillow官方ImageCms文档](https://pillow.readthedocs.io/en/stable/reference/ImageCms.html)

## 4 逻辑核心先独立

无论选A或B，业务核心都提供一致的项目读取、检查、布局规划、预览、导出、取消、检查点恢复与结果查询。任务传递结构化消息、项目相对资源或受控工作路径；不拼接shell命令，不通过消息反复传大图编码文本。

UI只决定用户如何修改草稿和查看进度；不自行计算逐色针数、不复制一份尺寸公式、不用浏览器截图代替生产TIFF/PDF。

原脚本的numpy、Pillow、PDF和Excel处理逻辑可逐项抽取。当前macOS字体绝对路径、固定DPI/格距、开发环境模块路径必须移除；不能把旧项目目录加入安装程序的隐含搜索路径。

## 5 构建与发布矩阵

采用各平台构建环境分别产出和测试的方案，不以在一台Mac上交叉编译所有包作为前提。

| 目标 | 预期产物 | 必须验证 |
|---|---|---|
| Windows x64 | 可运行应用与安装包，具体安装格式待选型 | 干净系统、非管理员用户目录、中文/空格路径、无Python运行、资源完整、卸载不误删项目 |
| macOS arm64 | `.app`及分发容器，具体容器待定 | 干净系统、应用目录/用户目录权限、外置路径、无开发环境、字体/ICC、沙箱/签名策略 |
| macOS x64 | 若纳入范围，单独包或经验证的通用包 | 所有Python/图像依赖架构一致，不能只合并外壳宣称通用 |

对外分发前分别完成适用的签名与平台发布流程；账户、证书和更新密钥由产品方管理，不写进仓库或作品包。本文件不在设计阶段创建账号、购买服务或提交商店。

更新必须保留用户项目、预设及旧任务；格式迁移先写新副本。检查更新与下载可以联网，离线使用不依赖频繁在线校验。自动更新是否首发由发布试验决定，手动下载安装始终保留。

## 6 字体、色彩与双端一致性

- 生产用字体明确绑定文件内容和排版度量；不能Windows默认微软雅黑、macOS默认Arial后还假定页数与换行相同。字体随包或客户导入的方式及发行条件开发前确认。
- ICC作为项目资源使用确切字节；系统显示色彩管理与生产文件嵌入配置分开。
- 图块、边界坐标、图例测量和材料公式来自同一核心计划，UI缩放不影响生产。
- 窗口、文件对话框可以原生；像素级生产渲染不依赖截图、系统打印对话框或屏幕DPI。
- 文件/ZIP的整体SHA可以因编码和元数据差异不同；核对业务矩阵、物理尺寸、窗口、解码像素与公式。要求确定性的符号内区建立跨端精确样本。

## 7 开发前的选型试验

以下为验证矩阵；本地已完成部分见12/15与TODO。v0.5将其中真实AI项归二期，其余相关本地/双端项仍服务一期：

1. 用同一份小母版和同一字体/ICC，先在A中做“打开→编辑参数→预览→取消→导出”的最小试验；达到明确的备选触发条件后，B才做同样本对照。
2. 加载240×320与更大针格样本、55/66色图例、符号库表格，测量UI响应和工作进程内存；不先把整张高分辨率图复制多份进视口。
3. 在Windows/macOS各构建独立应用，干净环境运行，验证无需Python、字体和外部旧项目目录。
4. 交换作品包，核对数字、资源、符号与分页；验证重开、升级、中文路径和故障恢复。
5. 记录A的实际安装/运行体积、实现复杂度、预览交互和可维护性；若触发B再作对照，证据满足需求后冻结选型。
6. 二期用真实候选服务验证图片输入/生成/编辑、预算、网络中断恢复及不携带凭据的跨端项目交换；不能只在开发者聊天工具里演示。AI服务边界见 [11](11-模型接入与质量评估.md)。
7. 验证项目单写入协调器与并发故障样本S18；确定颜色规范化、alpha/采样/量化基线并记录构建指纹，S20双端矩阵一致后才进入正式制版。

选型试验的通过条件是能独立运行并保留业务正确性，不是只打出两个空窗口。之后才锁定版本、依赖、构建流水线与正式代码目录。
